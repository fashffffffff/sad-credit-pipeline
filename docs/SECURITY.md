## 2. Меры защиты

|ID|Угроза|Мера|Остаточный риск|
|-|-|-|-|
|U-1|дискриминация|Пол, национальность, религия, место рождения, ФИО, адрес **не собираются**. Семья — максимум 5 баллов разницы, за детей не штрафуем. ML-подсказка учится только на кредитной истории.|низкий|
|U-2|утечка ПДн|**Номер паспорта не покидает устройство клиента**: браузер считает отпечаток по протоколу OPRF (RFC 9497) — сервер видит случайные байты, а отпечаток нельзя перебрать без ключа отдельного сервиса-токенизатора. Телефон — HMAC + маска. Полные номера паспорта и телефона в логи, журнал вызовов и аудит не пишутся. Идентификаторы, доход и результаты решения остаются данными клиента и требуют защиты. Наружу — только маски.|низкий|
|U-3|подделка заявки|СМЭВ проверяет связь паспорта и клиента (MISMATCH → отказ). Антифрод: граф связей заявок по отпечаткам устройства, телефона, паспорта + модель (PCA + kNN к эталонам схем + IsolationForest) → MANUAL_REVIEW. Одна активная заявка на паспорт.|средний (первые 1–2 заявки схемы неотличимы от честных)|
|U-4|подбор параметров|Сценарий «подбор» в антифроде (много заявок одного паспорта с растущим доходом); лимит 60 заявок в минуту на клиента; одна активная заявка на паспорт; предварительный расчёт до подачи не трогает БКИ — подобрать «проходной» скор нельзя. Встречное предложение даёт банк сам, поэтому подбирать незачем.|низкий|
|U-5|аудит|Журнал append-only с хэш-цепочкой: каждая запись содержит хэш предыдущей, проверка цепочки показывает первую испорченную запись. Удаления нет ни у одной роли. Решения не перезаписываются — хранятся версии.|низкий|
|U-6|таймаут / подмена ответа|Таймаут 3 с, 2 попытки, затем NEED_MORE_DATA (не отказ и не одобрение) и автоповтор. Запросы и ответы подписаны HMAC-SHA256 с меткой времени (защита от подмены и повтора); неверная подпись → ошибка + событие безопасности.|низкий|
|U-7|захват аккаунта|Клиент — без паролей: подтверждение номера звонком (SMS.RU); вход через Telegram и OAuth (Яндекс ID, VK ID — одноразовый `state` и PKCE) реализован, но на стенде выключен. Сотрудники: bcrypt, блокировка на 15 минут после 5 ошибок, 10 входов в минуту с IP, JWT 60 минут, «выйти на всех устройствах».|низкий|

## 3. RBAC — матрица прав

|Действие|Клиент|Сервис (system)|Андеррайтер|Аудитор|
|-|-|-|-|-|
|Подать заявку|да|да (симулятор нагрузки)|нет|нет|
|Посмотреть своё решение|да (только свои, по client_id)|да|да|да|
|Пересчитать решение|нет|да (автоповтор после таймаута)|да|нет|
|Читать аудит|нет|нет|нет|да|
|Менять правила скоринга|нет|нет|нет|нет — только через код и ревью; версия правил записывается в каждое решение|
|Удалять аудит|нет|нет|нет|нет (append-only)|

Дополнительно: ручное решение по MANUAL_REVIEW — только андеррайтер; антифрод-детали и ML-подсказку клиент не видит никогда. Каждый отказ в доступе (403) пишется в аудит. Служебная роль «администратор стенда» (хаос-режим, симулятор) существует только для демонстрации и в матрицу банка не входит.

## 4. Аудит — структура события

|Поле|Тип|Пример|Зачем|
|-|-|-|-|
|event_id|string|evt_0001|уникальный ID|
|app_id|string|app_0001|привязка к заявке|
|action|enum|decision_made|что произошло: application_created / decision_made / recalculated / reviewed / offer_accepted / certificate_issued / login / access_denied …|
|decision|enum|APPROVED|какое решение зафиксировано|
|reason|string|HIGH_DTI|код причины из `08_reasons.md`|
|score|integer|90|итоговый балл|
|dti|number|0.21|долговая нагрузка|
|actor|string|system|кто: system / client / underwriter / auditor|
|at|string (ISO 8601)|2026-11-09T10:00:00Z|когда|
|prev_hash, hash|string|`9f2c…`|хэш-цепочка: подмена любой записи ломает все последующие хэши|

**Правила аудита:**

* Как хранится журнал? **Append-only**: только добавление; изменение обнаруживается проверкой хэш-цепочки.
* Сколько хранится? **5 лет** — проектная политика хранения. Автоматический регламент архивирования и удаления для промышленной эксплуатации требует отдельной реализации.
* Содержит ли ПДн? **Нет открытых паспортных и телефонных номеров**: журнал содержит `client_id`, `app_id`, коды и числа решения. Это псевдонимизированные данные, а не гарантия юридического обезличивания.
* Кто имеет доступ на чтение? **Аудитор** (и система при проверке цепочки).

## 5. Защита данных

**Что нельзя хранить и почему?**

* PAN / номер карты — не нужен для предварительного решения; хранение требует сертификации PCI DSS, утечка = прямой ущерб клиенту.
* Оригинал паспорта — его даже в зашифрованном виде хранить нельзя: ключ шифрования тоже можно украсть. У нас паспорт не попадает на сервер вовсе (OPRF в браузере).
* Полное ФИО + телефон + адрес — вместе это готовый профиль для мошенника и социальной инженерии; для решения не нужны.

**Что можно хранить?**

* `passport_hash` — отпечаток нельзя обратить в номер и нельзя перебрать без ключа токенизатора; нужен для дублей, СМЭВ, БКИ, антифрода.
* `income` — нужен для расчёта DTI и балла; это число без привязки к ФИО.
* `decision`, `reason`, `score`, `dti` — результат и объяснение решения; без них нельзя ответить клиенту и регулятору.

**Маскирование логов — пример:**
До: `POST /api/v1/applications phone=+79991234567 passport=4510 123456 income=120000`
После: `POST /api/v1/applications client=cli_0001 passport_hash=f727a8… app=app_0001 status=201` — паспорта на сервере нет в принципе, телефон заменён номером клиента, доход в логи не пишется.

## 6. Секреты и ключи

|Секрет|Где хранится|Кто имеет доступ|Ротация|
|-|-|-|-|
|HMAC-ключи подписи БКИ/СМЭВ/токенизатора|переменные окружения на сервере (`*_HMAC_SECRET`), файл `credit.env` с правами только для службы|backend и соответствующий сервис|раз в 90 дней и сразу при подозрении (окно на смену — оба ключа валидны)|
|Ключ OPRF (паспорт)|только у сервиса-токенизатора: `OPRF_PRIVATE_KEY` или `secrets/oprf.key` (права 600)|только токенизатор; backend его не знает|при компрометации — с перевыпуском отпечатков (поэтому ротация редкая)|
|JWT-секрет|env `JWT_SECRET`|backend|раз в 90 дней (все сессии разлогинятся)|
|`PII_PEPPER` (отпечаток телефона)|env, резервная копия в менеджере паролей владельца|backend|не ротируется без пересчёта отпечатков|
|Ключ подписи справок Ed25519|`CERT_SIGNING_KEY` или `secrets/cert_ed25519.key` (600)|backend|раз в год; открытый ключ публикуется на `/verify`|
|Пароль БД|в SQLite пароля нет — файл доступен только учётной записи службы; в PostgreSQL — env `DATABASE_URL`|backend|раз в 90 дней|
|Ключи Telegram, SMS.RU, Яндекс ID, VK ID|env на сервере|backend|при смене ответственного или подозрении|

**Правила:**

* Секреты коммитятся в Git? — **Нет** (`.env`, `secrets/` в `.gitignore`; в `.env.example` только закомментированные заглушки).
* Секреты логируются? — **Нет**.
* В коде — только `os.environ`? — **Да**; демо-значения разрешены только вне production, при `APP_ENV=production` сервис со слабым или демо-секретом не запускается.

1. «У нас всё безопасно» — нет: 7 угроз, у U-3 остаточный риск средний, и мы честно пишем почему.
2. Угрозы без оценки — у всех есть вероятность и ущерб.
3. Меры не привязаны — каждая мера по ID.
4. Нет RBAC — 4 роли, проверка на каждой ручке, 403 пишется в аудит.
5. Нет `actor` и `at` — есть.
6. Паспорт «в зашифрованном виде» — у нас паспорта на сервере нет вообще.
7. Секреты в коде — нет; при production демо-секрет не даст запустить сервис.
