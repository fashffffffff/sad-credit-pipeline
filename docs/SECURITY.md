# Безопасность: ситуации, ошибки, решения

Модель безопасности системы: роли, защита данных, обработка сбоев.

## 1. Ситуация → Ошибка → Решение

| Ситуация | Что происходит / какая ошибка | Решение в системе |
|---|---|---|
| Упал шлюз СМЭВ или БКИ (HTTP 503, обрыв соединения) | запрос не проходит, этап `fail` | таймаут 3 с, до 2 повторов (паузы 0,3 и 0,6 с); если не помогло — заявка в `manual_review` с причиной `SMEV_UNAVAILABLE`/`BKI_UNAVAILABLE`, сервер не падает, клиент не теряется |
| Внешняя система «висит» (таймаут) | ответа нет | тот же механизм; проверено вживую: 3 попытки, ≈ 11 секунд, итог `manual_review` |
| Подделка ответа внешней системы | подпись HMAC-SHA256 ответа не сходится (`bad_signature`) | ответ отвергается без повторов, заявка в `manual_review` (`BAD_SIGNATURE`), запись в журнал аудита, SSE-событие `security` на дашборд; подписываются оба направления, время в подписи (окно 5 минут) защищает от повтора старых ответов |
| Повтор запроса (двойной клик, сбой сети) | дубль заявки на один кредит | заголовок `Idempotency-Key`: тот же ключ и то же тело → тот же ответ, заявка не создаётся второй раз; другое тело → 409 |
| Неверные или вредные данные во входе | мусор в анкете | строгая валидация (формат, диапазоны, контрольная сумма ИНН) → 422 с русскими сообщениями по полям; параметризованные SQL-запросы |
| Утечка базы данных | злоумышленник получил файл БД | паспорт хранится только как `HMAC-SHA256(PII_PEPPER, паспорт)` (перец — вне БД, в переменной окружения), ФИО и телефон — только маски, дата рождения не хранится, пароли — bcrypt с солью |
| Чужая роль пытается выполнить действие | HTTP 403 (без токена или с поддельным — 401) | проверка ролей RBAC на сервере в каждой ручке; каждый отказ пишется в аудит (`access_denied`) и летит в SSE как `security/forbidden`; токен JWT подписан (алгоритм зафиксирован HS256, `exp` обязателен), живёт 60 минут |
| Подделка записей журнала аудита | запись изменена или удалена | хэш-цепочка: `hash = sha256(prev_hash + запись)`; `GET /api/audit/verify` возвращает `ok=false` и `broken_at` — номер первой сломанной записи (проверено вживую) |
| Подбор пароля | много попыток входа | 5 неверных паролей подряд → блокировка логина на 15 минут (429 + запись в аудит), не больше 10 попыток в минуту с одного IP; ответ на неверный логин и неверный пароль одинаковый; блокировка работает и для несуществующих логинов — логины не угадать (проверено вживую) |
| Украденный токен | токен у чужого человека | JWT живёт 60 минут; `POST /api/auth/logout-all` увеличивает `token_version`, и все выданные токены сразу перестают работать |
| Выдуманный паспорт или опечатка | несуществующий регион серии, невозможный год бланка, код подразделения чужого региона, дата выдачи раньше 14-летия | строгая проверка в `common/passport.py` → 422 с русским сообщением на конкретное поле; настоящие корректные данные проходят всегда |
| Просроченный паспорт | паспорт не заменён после 20/45 лет | СМЭВ возвращает `passport_valid=false` → отказ `PASSPORT_INVALID` «Паспорт просрочен» |
| Повторная заявка по одному паспорту | дубль, обход отказа повторной подачей | 409 `duplicate_application` с `existing_id`, пока заявка в работе или отказ был меньше 30 дней назад |
| Слишком большой или «грязный» запрос | тело > 64 КБ, лишние поля | 413 без разбора тела; `extra="forbid"` — лишние поля дают 422; заголовки `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` |
| Кредитная фабрика (организованная группа, заявки на подставных людей) | каждая заявка по отдельности чистая | антифрод по графу связей (HMAC-отпечатки устройства, телефона, ИНН, паспорта) и поведению: подозрительные заявки уходят в `manual_review` с объяснением `FRAUD_SUSPECT` — предупреждение, не отказ; в графе нет открытых данных (проверено вживую: 15 сценарий) |
| Самозапрет на кредиты | клиент запретил выдачу кредитов через Госуслуги | БКИ присылает `self_ban`; жёсткий стоп-фактор `SELF_BAN` → отказ |
| Неверное решение по статусу | попытка вернуть одобренную заявку в обработку | машина статусов: запрещённый переход → HTTP 409; ручное решение — только `risk_manager` |
| Сбой модели или пакета ML | модель не загружается | этап `scoring` = `fail`, заявка в `manual_review` (`SCORING_UNAVAILABLE`); `/api/health` показывает `model: unavailable` |
| Неожиданная ошибка внутри конвейера | исключение в коде | общий перехват: заявка уходит в `manual_review` (`PIPELINE_ERROR`), а не зависает в `processing` |

Результаты полного аудита кода (находки, воспроизведение, тесты) — в `docs/SECURITY_AUDIT.md`.

## 2. Матрица ролей (RBAC)

| Действие | operator | risk_manager | auditor | admin |
|---|:-:|:-:|:-:|:-:|
| Создать заявку | ✅ | – | – | ✅ |
| Смотреть заявки | свои | все | все | все |
| Решение по ручной проверке | – | ✅ | – | – |
| What-if (ползунки модели) | ✅ | ✅ | – | ✅ |
| Информация о модели, статистика | ✅ | ✅ | ✅ | ✅ |
| Журнал аудита и проверка цепочки | – | – | ✅ | ✅ |
| Хаос-панель, массовая симуляция | – | – | – | ✅ |

Учётки (по одной на роль) генерируются при первом запуске: логин вида `op.7f3a9c`, пароль 24 символа из `secrets.token_urlsafe`.
Лежат в `secrets/credentials.local.json` и `.md` (права 600, папка в `.gitignore`), в логе — только путь к файлу. В БД — bcrypt-хэши.

**Почему так:**
- *Секреты не в репозитории.* Публичный пароль вида `admin123` знает каждый, кто видел код, — это та же дыра, что и публичный секрет JWT. Файл с учётками создаётся локально и не коммитится.
- *Уникальные длинные пароли и bcrypt.* Случайные пароли не подобрать, а хэш с солью бесполезен при утечке БД.
- *Без самостоятельной регистрации.* Аккаунты сотрудникам выдаёт администратор — в банке так принято: «кто угодно создал себе учётку» недопустимо.
- Старые демо-пароли (`логин+123`) при старте на существующей БД автоматически выводятся из строя: пользователи с таким паролем удаляются, вместо них создаются учётки из файла.

## 3. Что записывается в аудит

Вход, неудачный вход, блокировка логина, отказ из-за лимита по IP, выход со всех устройств, создание заявки, каждое автоматическое решение, ручное решение, смена хаос-режима, запуск симуляции,
ошибка подписи ответа, каждый отказ в доступе (403). В записях только маски и идентификаторы, без паспортов.

## 4. Известные ограничения

Счётчики блокировок и лимит по IP хранятся в памяти процесса (после перезапуска сбрасываются); за прокси адрес клиента нужно брать из доверенного заголовка; секреты лежат в переменных окружения, а не в хранилище секретов;
удаление самых последних записей аудита цепочка не обнаружит (защита — периодически выгружать последний хэш во внешнее хранилище).
