# Подбор кредита с приоритетами (03.11)

Запрос пользователя: исправить 0 ₽ / 0% на заполненной форме; порядок сумма → доход → продукт → срок; в конце шкала важности суммы относительно срока и соответствующие рекомендации.

Решение: сохраняем 4 шага; на первом переставляем поля, не сбрасываем выбранный продукт без объяснения. На подтверждении — один ползунок 0…10 с исходным значением 8: `amount_priority`, важность срока = 10 − значение. Учитывается в подборе, не влияет на скоринг и правила принятия решения. Сроки ограничены products.csv (максимум 60 мес.); сумма ограничена также 10 доходами.

Quote API (`POST /api/v1/quote`) принимает поля анкеты без паспорта, необязательный amount_priority (целое 0…10, default 8), profile_complete (bool, default true), age_known (bool, default true). Для раннего расчёта frontend передаёт профиль с временными значениями, но profile_complete=false, age_known=false до даты рождения и не показывает фиктивный балл.

Ответ Quote сохраняет поля, добавляет:
- status: ready | needs_data | product_mismatch
- dti, monthly_payment, partial_score: number|null. null никогда не отображается как 0.
- fields: словарь точных сообщений по полям.
- eligible_products: продукты, подходящие по возрасту/доходу И сумме (срок не блокирует выбор до его ввода).
- recommendations: до 3 предложений, status preliminary, сумма/срок/ставка/платёж/dti/переплата/итого; они проверены только по известным анкетным правилам, БКИ и СМЭВ ещё не проверялись.
- recommendations и offers используют amount_priority для ранжирования: вес относительного уменьшения суммы против относительного увеличения срока. Дубликаты убираются, сохраняются альтернативы с разным компромиссом.
- Каждый вариант: product_id, product_name, amount, term, rate, monthly_payment, dti, score, total_payment, overpayment, amount_delta, term_delta, explanation, preliminary (для quote всегда true). amount_delta/term_delta = вариант − запрос.

Если формат корректен, но срок/сумма не подходят продукту, числовой расчёт всё равно возвращается со status=product_mismatch и fields.product_id. Это не отказ банка. Ввод отсутствует/сломанный формат → status=needs_data и null; действительный 0 не используется как заглушка.

Встречные предложения после отказа и рекомендации до подачи используют один подборщик. Приоритет сохраняется в заявке (миграция SQLite ADD COLUMN с default 8); при принятии предложения переносится. Предварительные варианты не обещают одобрение. Кейсные правила и исходный CSV остаются прежними.

Проверки: точный кейс скриншота 5 млн, 3 мес., доход 3.43 млн, premium → ненулевой платёж + сообщение о сроке минимум 12 мес.; переключение приоритета меняет порядок вариантов; при высоком приоритете суммы сохраняем сумму, если можно уложить в допустимый срок; миграция старой БД и принятие предложения сохраняют приоритет; mobile/desktop, нет 0/NaN/фиктивного отказа при неполных данных.

## План реализации и результаты
1. Регрессия quote: точные цифры со скриншота и условия продукта; сначала воспроизведено падение тестов.
2. Ядро подбора: перечисление допустимых сроков и сумм по продуктам, проверка неизменёнными правилами, ранжирование по предпочтению и устранение одинаковых компромиссов.
3. API и SQLite: новый параметр, проверка типа/границ, безопасное добавление колонки к существующей базе, перенос предпочтений во встречные заявки. Отдельный тест сохранения старых записей.
4. Frontend: порядок полей, компактный выбор продукта, состояния расчёта без ложных нулей, приоритет и рекомендации на последнем шаге. Пустой возраст не превращать в фактический возраст 30 лет при выборе специальных продуктов.
5. Проверки: полный pytest, check/build, браузерный сценарий скриншота, обе крайности предпочтений, применение без потери анкеты/паспорта, mobile/desktop, обновление сервера с сохранением данных.
